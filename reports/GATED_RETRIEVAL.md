# Gated retrieval: L5M vs vector-DB metadata filtering

**The benchmark our other benchmarks couldn't show.** LongMemEval/ConvoMem
share one tenant and no policies, so they never exercise the gates. This
benchmark measures the differentiator directly: multi-tenant, multi-policy
retrieval where some memories must *never* come back — and it runs entirely
on local compute (zero API cost, fully reproducible).

## Setup

Synthetic corpus generated by `l5m-bench` (deterministic, seeded): **100,000
memories across 100 tenants**, with realistic gate diversity — some memories
are low-trust (below the probe's trust floor), expired (`valid_until` in the
past), not-yet-valid (`valid_from` in the future), or policy-restricted
(mask disjoint from the probe's). 200 needle queries, each targeting one
specific memory in one tenant; ground truth includes whether the target is
**embargoed** (a gate should hide it — the *correct* answer is to refuse).

Both systems get the identical corpus, queries, and ground truth
(`l5m-bench --export-corpus`):

- **L5M**: one compiled segment; tenant/trust/temporal/policy gates run
  inside the engine before scoring.
- **Chroma + all-MiniLM-L6-v2** (local ONNX): one collection, tenant as
  metadata; queried two ways — `where={"tenant": t}` on every call (the
  vector DB done *right*), and once with the filter forgotten on a code path
  (the classic multi-tenant RAG bug).

## Results (100K memories, 100 tenants, 200 needle queries, top-k 8)

| | L5M (gates in engine) | Chroma, `where` filter | Chroma, filter forgotten |
|---|---|---|---|
| Query p50 | **0.28 ms** | 129 ms (460×) | 104 ms |
| Query p95 | 0.32 ms | 144 ms | 113 ms |
| Clean-needle recall@8 | 0.51† | **0.82** | 0.08‡ |
| **Embargoed memories disclosed** | **0 / 26** | **24 / 26 (92%)** | 4 / 26‡ |
| **Cross-tenant rows in top-k** | **0** (structural) | 0 | **1,573 / 1,600 (98%)** |
| Ingest/build (100K docs) | 3.2 s compile + 0.3 s open | 22.6 min (embedding) | same store |

‡ With the filter forgotten at 100-tenant scale, results drown in
cross-tenant noise: 98% of everything returned belongs to other tenants,
recall collapses to 0.08, and the only reason fewer embargoed memories
surface is that *other tenants' data* outcompetes them.

† Honest caveat: on this synthetic word-soup corpus, L5M's deterministic
fingerprints under-rank vs learned embeddings (a known synthetic-vocab
artifact — on real text, L5M's hybrid mode beats this same vector DB with
statistical significance; see `SCORE_ANALYSIS.md`). We report it anyway:
this benchmark's subject is the *gates*, and cherry-picking would defeat
the point.

## What the numbers mean

1. **A tenant filter is not a policy engine.** Even operated perfectly,
   the vector DB's `where={"tenant"}` can only express tenancy. Trust
   floors, validity windows, and policy masks don't exist in its model — so
   **92% of the memories that must be hidden** (expired facts, low-trust
   rumors, higher-clearance data) were retrieved and ranked like anything
   else. L5M refused all 26, structurally, before scoring.
2. **The forgotten filter is catastrophic, and it's one code path away.**
   Application-layer filtering means every query site is a place the
   isolation can silently vanish. In the engine, there is no filter to
   forget.
3. **Security is also the latency win.** The gate scan touches only the
   probe's tenant slice (~5 µs at this scale); the vector DB pays embedding
   inference plus ANN over the full index on every query.

## Reproduce (no API keys, ~30 min on a laptop)

```bash
cargo build --release -p l5m-bench
./target/release/l5m-bench --synthetic-capsules 100000 --tenants 100 \
  --needle --synthetic-queries 200 --iterations 1000 \
  --export-corpus runs/_gated_corpus_100k.json

pip install chromadb
python bench/gated_peer.py --corpus runs/_gated_corpus_100k.json --top-k 8
```
